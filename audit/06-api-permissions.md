## 2. Role probe results (spec §6.4: anonymous / other role)

`phase6-probe.json`, 417 rows × 3 roles:

- **Anonymous:** 365 → 401, 1 → 403, 16 → 404, 4 → 400, 31 → 200. **Every 200 is on an `AllowAny` row.** No private endpoint answered an anonymous caller.
- **Student on `IsTeacher` / `IsSuperAdmin` rows:** 0 successes (all 403).
- **Teacher on `IsSuperAdmin` rows:** 0 successes.
- **Matrix verdicts:** 362 `ok-role`, 53 `public`, 2 `CHECK`. Both CHECK rows have `permission_classes([])` by design:
  - `/api/auth/refresh/`: the refresh token itself is the credential.
  - `/api/panel/stop-impersonation/`: the `impersonator_id` claim is the credential (`panel/api.py:861-879`). See API-007.
- **5xx:** only `POST /api/learning/reels/quiz/` and its `v1` alias, for student and teacher (API-001).

What this probe proves: role and authentication enforcement on every DRF route. What it does not prove: object-level ownership with real foreign objects. That is covered by §3 (static review of every object-ID route) and by the targeted reproducers from Phases 3–5 and this phase.

## 4. Validation, mass assignment and response leaks

- **Mass assignment.** No `fields='__all__'`, no `**request.data`, and no generic `setattr` from request keys outside one superadmin campaign editor (`panel/api.py:5126`, fields whitelisted through `_campaign_lifecycle_fields`). Profile updates are whitelisted (`accounts/api.py:327-360`). `user`, `owner`, `role`, `is_staff`, `is_premium`, `balance`, `xp` and `coins` cannot be set by students. Admin-only edits of coins/role exist (`panel/api.py:779`, IsSuperAdmin). OK.
- **Response leaks.** Every student-accessible GET that returned JSON was scanned for `password`, `is_correct`, `correct_option_id`, `correct_index`, `reference_answer`, `accepted_answers`, `phone*`, `email`, `telegram_id`, `card_number`, `screenshot`, `admin_note`, `token`/`refresh`/`access`, and for another user's email (seeded `other@example.com`).
  - Hits: own `email` on `/me`, `/profile`, `/dashboard/home`, `/shop/inventory` (fine), and `card_number` on checkout (the merchant card the student pays to, intended).
  - No answer keys or other-user PII were found.
  - Limitation: the DB was sparse, so list endpoints with no rows could not leak anything. Answer-key exposure in the loop and sprint was checked in Phase 4: the key is revealed only after the first answer.
- **Error disclosure.** About 20 handlers return `str(e)` to the client, mostly superadmin panel routes (`panel/api.py:705, 2298, 2689-2714, 2986-3012, 3166, 3738, 3765, 3975, 4289, 4367, 4400, 4498`). User-facing ones are `learning/api.py:976` (reel comments) and `learning/api.py:1295` (post delete). There is no stack trace (DEBUG off in production, JSON renderer only).

## 5. Findings

### API-001 — Reels quiz returns 500 for every logged-in user, after XP and streak are already written; unknown `reel_id` pays
- **P2, CONFIRMED.** `backend/learning/api.py:906` reads `profile.streak_days`, a field that does not exist (the field is `streak`). The response therefore 500s for every authenticated call.
- XP and streak are written before the crash (`:900-904`).
- `correct_index` defaults to `0` when the reel does not exist (`:873`), so any unknown `reel_id` with `answer_index: 0` counts as correct.
- Repro: `logged-in reels quiz (unknown reel 999001, answer 0) -> 500 | xp after: 5 streak: 1`. The anonymous call returns 200 with `"+5 XP hisobingizga qo'shildi!"` while `xp_earned: 0` (misleading).
- Effect: the reels quiz feature is broken for all logged-in users (a 500 on every answer). Each new `reel_id` value pays 5 XP up to the daily cap (`reels_quiz` 30/day, so 150 XP/day) and bumps the streak (Phase 3 ECON-002).
- Fix: use `profile.streak`; return 404 for an unknown reel; build the response message from the real `xp_earned`. Regression: logged-in correct answer → 200; unknown reel → 404 and no XP.

### API-002 — A paid classroom mock's question set can be taken through the public test endpoint, without a subscription and before the scheduled time
- **P2. CONFIRMED when the reused `TestSet` is published; LIKELY in practice.** `MockTest.test_set` reuses an existing `TestSet` (`backend/classroom/models.py:244-246`, help text "Mavjud test to'plami qayta ishlatiladi"). `POST /api/tests/<id>/start/` (`tests_app/api.py:308-360`) checks published/archived, PRO and per-test purchase, but **not classroom membership, subscription or `scheduled_start`**.
- Repro (non-subscriber, mock scheduled +2 days, set `is_published=True`, `is_premium=False`): `classroom start -> 404 | /api/tests/<test_set>/start/ two days before mock -> 200 ['attempt_id', 'mode']`.
- Effect: the teacher's paid weekly mock leaks early (questions, then answers after finish), which breaks exam integrity and the revenue share. Unpublished sets are safe (`:314-316`), but nothing forces teachers or admins to keep them unpublished.
- Fix: in `start_test_api` (and the catalogue), refuse or hide any `TestSet` referenced by a non-free `MockTest`, unless the caller has class access and the mock window is open. Alternatively, make classroom mocks use a copied, unpublished set. Regression: the reproducer must return 403/404.

### API-003 — Top-level JSON array crashes 61 endpoints with 500
- **P3, CONFIRMED.** `[1,2]` as the body produces `AttributeError: 'list' object has no attribute 'get'` on 61 POST/PUT/PATCH routes (list in `phase6-leaks-and-bodies.json`). These include auth login/register/google/telegram, profile, tests start/answer, sprint and loop answer, growth, battles, learning feed/reels/study/flashcards, games and analytics.
- Effect: unauthenticated 500s on demand (login and register are AllowAny), noisy alerting and DoS amplification of error logging. No data is corrupted.
- Fix: one global guard — a DRF parser or middleware that rejects non-object JSON on these views (or a small `@require_json_object` decorator). Regression: the sweep test expects no 5xx.

### API-004 — No server-side length limits on free-text input
- **P3, CONFIRMED.** A 200 000-character `first_name` was accepted and stored (`accounts/api.py:328-330`; SQLite does not enforce `max_length`). On production Postgres the same request hits the `varchar(150)` limit and returns 500 instead of 400 (LIKELY; not run on Postgres). A 200 000-character feed caption is accepted and stored as-is (`learning/api.py:1139`, TextField). The JSON body limit is 20 MB (`settings.py:483`).
- Fix: validate lengths at the API (serializers or explicit `[:N]` with 400 on overflow).

### API-005 — The growth open-question grader compares against `explanation`, not `reference_answer`
- **P3, CONFIRMED.** With `question_id` given and no client reference, `growth/views.py:39-40` uses `q.explanation`. Repro: question with `reference_answer="1402-yil"`: `'1402-yil' -> False`. The correct answer was marked wrong, because the explanation sentence is the target (AI mocked, fallback ratio).
- Same endpoint: the client may send its own `reference_answer` (`:30`). It also works as a 60/day `is_correct` oracle for any `question_id`, but that oracle is weak today because of this bug. Phase 2 GRADE-008 covers the grader itself.
- Fix: use `q.reference_answer` plus `accepted_answers`; ignore any client-sent reference when `question_id` is present.

### API-006 — Raw exception text in API responses
- **P3, CONFIRMED (code).** See the line list in §4. User-facing cases: `learning/api.py:976` and `:1295`. Effect: internal details (DB errors, paths) leak to clients; low risk with DEBUG off.
- Fix: log the exception and return a generic message.

### API-007 — Impersonation tokens are long-lived superadmin credentials
- **P3, CONFIRMED (code).** `user_impersonate_api` (`panel/api.py:846-858`) issues a normal 30-day refresh token for the target user with an `impersonator_id` claim. `stop-impersonation` (`:861-879`) turns any token carrying that claim into **fresh superadmin tokens**. SimpleJWT copies custom claims from refresh into new access tokens, so the claim survives refreshes.
- With no revocation (Phase 5 AUTH-002), an impersonation session that leaks (shared device, an XSS in the impersonated UI, logs) is a 30-day path to superadmin.
- Mitigations already present: the original admin must still be active and superadmin (`:871-877`), and impersonating other admins is blocked (`:849`).
- Fix: short TTL (≤ 1 h, no refresh) for impersonation tokens, plus blacklist on stop.

### API-008 — Class battle room state is readable by any authenticated user
- **P3, CONFIRMED (code).** `core/views.py:239-241` has no participant or owner check, and room IDs are sequential. Exposure is limited to room state (participants, scores). Joining needs the PIN.

## 6. Coverage statement

- **Fully covered for role/authentication enforcement:** every DRF route (417 method+path rows) — see the matrix.
- **Covered statically for ownership:** every non-admin route with an object ID (§3). Superadmin routes (153) were role-checked only; their internal business logic (for example bulk deletes and broadcasts) is not audited beyond the reproducers above.
- **Not covered:** pagination/filter abuse on large datasets (sparse test DB), file-upload content checks beyond `validate_screenshot`, and the Django admin itself.

## 7. Summary

- Authentication and role enforcement are consistent across all 417 DRF routes: no anonymous access to private routes and no student or teacher escalation.
- No API IDOR was found. Object lookups are owner-scoped. Mass assignment is not possible. Student GET responses expose no answer keys or other users' PII (sparse-data caveat).
- New findings:
  - **API-001 (P2):** reels quiz 500 for everyone, plus free XP for fake reel IDs.
  - **API-002 (P2):** paid classroom mock test sets can be started through the public endpoint before schedule and without a subscription.
  - **API-003–008 (P3):** JSON-array 500 on 61 routes, no length limits, wrong reference in the growth grader, `str(e)` leaks, long-lived impersonation tokens, readable room state.
- The most serious authorization issue remains Phase 3 SEC-PAY-001 (P0, Telegram).
